# Review: host-aware setup design, revision 3 (Codex)

Revision 3 is not implementation-ready. Its central claim—install directories enforce role isolation—is false for documented host overlaps, and the reviewer-only Codex row does not satisfy the existing `Host` or boundary contracts.

## Blockers

1. **Install-directory isolation does not hold on a machine with several hosts.** Section 6A says directory choice decides visibility and calls `~/.claude/skills` invisible outside Claude and `~/.agents/skills` invisible to Claude (`design.md:139-150`, ADR-6 at `:226-232`), but the verification says Copilot recognizes project `.claude/skills` and `.agents/skills`, personal `~/.agents/skills`, and—on VS Code's Claude harness—`~/.claude/skills` (`verification-2026-11-17.md:44-47,68-72`). Thus Copilot can discover both the home coding skill and the Codex review skill; a multi-host machine also retains old modules because no removal contract exists. NFR-11 tests only where files are written, not every host that can read those paths (`design.md:264`). **Fix:** replace “isolation” with an explicit host×directory visibility matrix, define install/removal for every selected-host combination, and make NFR-11 assert absence from every unintended host's documented scan set.

2. **The promised reviewer isolation fails for `reviewer_provider=claude` and at work.** The review skill is deliberately co-located with the coding skill in `~/.claude/skills` for a Claude reviewer and in `~/.copilot/skills` for a Copilot reviewer (`design.md:147-150,161`); descriptions are routing hints, not access control. The guard forbids `skill/`, not the installed `python-code-standards` skill, and its “unless a change touches them” exception authorizes reading the coding guide precisely when that guide changes (`design.md:152`). This contradicts the absolute requirement at `design.md:135` and analysis resolution at `analysis.md:93`, while NFR-13 merely checks that the review package does not import or name the guide (`design.md:266`). **Fix:** either weaken the requirement to best-effort non-invocation and test that claim, or use a genuinely separate reviewer process/home with no coding skill installed; provider `claude` cannot meet the current requirement in the same skill home.

3. **A reviewer-only Codex row is not a valid row under the specified model.** `Host` requires coding-host fields including `.claude`/`.copilot` home, defaults, providers, suggestions and gate text (`design.md:111`), while the Codex row introduces `roles`, `$CODEX_HOME`, a different instruction filename, and “no model questions” (`design.md:154`)—fields/behaviour absent from that contract. `ask_choices` always consumes host model choices (`design.md:102`), `stored_choices` fills missing model defaults (`:103`), `plan_host` takes choices (`:104`), and `selected_hosts` falls back to `claude-code` (`:100`); sections 1 and 6 still define only two coding hosts (`:7-12,113-123`). ADR-1's claim that Codex is a small row (`:186-192`) is therefore unsubstantiated. **Fix:** model coding hosts and reviewer targets as separate types/contracts, or fully extend every boundary, state, count, and test to cover a role-only host without `ModelChoices`.

4. **The guard/focus mechanism cannot enforce the stated Codex review boundary, and the “bundle” is unspecified.** The spec correctly concedes that Codex may open any repo file (`design.md:160,278`) but still resolves “must not read” via advisory text (`analysis.md:93,95`). The companion's plain `review` accepts no focus; its `adversarial-review` command interpolates focus into a prompt, but that does not invoke the separately installed `adversarial-review` skill or automatically add `review_brief.py` output. No contract says who runs the brief, how its output enters the prompt, or how skill activation is verified (`design.md:156,234-248,295`). **Fix:** specify the exact executable command and constructed prompt inputs; call the skill explicitly if it is required, and restate the guarantee as advisory unless the reviewer runs in a filesystem/home that lacks the guide.

## Should-fix

5. **Section 6A overstates the verified loading facts.** “Codex loads only `AGENTS.md`” omits configured fallback filenames (`design.md:141`; `verification-2026-11-17.md:13,17-18`), and the host comparison omits that Claude Code v2.1.277+ reads project `AGENTS.md` when no project `CLAUDE.md` exists, or via import when one does (`verification-2026-11-17.md:57-58`). “Never” and “invisible” are therefore configuration-dependent, not verified absolutes. **Fix:** qualify the claims with default/fallback/import conditions and carry those conditions into ADR-6 and the visibility tests.

6. **The guard can suppress relevant review evidence and still misses auto-loaded evidence.** Its blanket list treats an entire `skill/` tree as “other agents' instructions” (`design.md:152`), although that tree also contains executable tooling and templates relevant to changes; meanwhile Codex receives applicable `AGENTS.md` before the task, so a focus string cannot prevent that content from already being loaded (`verification-2026-11-17.md:11-16`). **Fix:** guard only specific foreign instruction artifacts, remove the change-touches exception if strict isolation is intended, and document that automatically injected instructions are outside the guard's control.

7. **The new installer is under-specified and duplicates host selection/state.** A second command is proposed to plan module destinations (`design.md:178,294`) even though setup already detects/selects hosts and writes their instruction homes; the spec gives it no boundary contract, state transition, atomicity/failure semantics, stale-file policy, or relationship to `HOSTS`. That creates a second configuration path and makes “only the chosen host's files” untestable across reruns (`analysis.md:91-92`). **Fix:** either fold module planning into the existing per-host `Plan`, or specify the installer as a first-class boundary with the same selection, confirmation, atomic-write, stale-removal, and summary contracts.

8. **Missing risks: routing is nondeterministic and reviewer invariants can anchor the result.** The risks mention shared directories and drift (`design.md:277-280`) but not false-positive/false-negative skill activation from descriptions, coexistence of several host homes, stale modules after provider changes, `CODEX_HOME` differing between setup and the review process, or a reviewer definition-of-done biasing an “independent” adversarial review. **Fix:** add these risks with observable mitigations (activation evals, resolved-home reporting, uninstall/update tests, and a review test containing violations outside the invariant list).

## Nit

9. **The 300-word review skill, guard in three files, host references, installer, drift test, and focus plumbing are more machinery than the guarantee achieved.** The design still admits same-directory discovery and unrestricted repo reads (`design.md:149-161,277-280`). **Fix:** prefer one explicit adversarial-review prompt/bundle and separate reviewer home; add reusable skills only after an activation eval demonstrates value.

## What Codex actually loads

In this Codex session I receive system/developer/user messages plus discovered `AGENTS.md` instructions injected root-to-leaf; I initially see skill metadata, load a full `SKILL.md` only when invoked/matched, and read repository files only through tools I choose. Official Codex behavior in the verification matches that model (`verification-2026-11-17.md:11-18,25-28`). Consequently, a global guard can influence voluntary reads but cannot retract injected instructions, hide overlapping skill metadata, or provide filesystem isolation.
